# ASEA 통합 업무 플랫폼 — PR부터 자동 배포까지 운영 지침

적용 범위: `asea-college/asea` 저장소의 현재 및 향후 모듈(`notice`, `hr`, `budget` 등).

## 개발 작업 완료의 정의
사용자가 기능 개발·수정을 지시하면, 별도의 중간 승인 요청 없이 가능한 범위에서 다음 작업을 연속 수행한다.

1. 실제 기본 브랜치와 현재 배포 상태를 조회한다.
2. 기능 브랜치에서 코드를 작성하고 검증한다.
3. GitHub에 커밋·푸시하고 PR을 생성한다.
4. 자동 테스트, 보안 검사, 빌드 결과를 확인하며 실패 시 수정한다.
5. 필수 검증이 성공하면 PR을 기본 브랜치에 병합한다.
6. GitHub Actions 등 CI/CD를 통해 해당 서비스의 목표 환경에 자동 배포한다.
7. 배포 URL/릴리스/아티팩트의 상태와 주요 기능을 확인하고 결과를 보고한다.
8. 기준 커밋·버전·서버 마이그레이션·검증 결과·알려진 문제·복구 경로를 기록한다.

**PR 생성만으로 완료라고 보고하지 않는다.** 개발, 테스트, 병합, 배포, 배포 후 검증을 각각 실제 수행한 경우에만 완료로 표기한다.

## 최초 구축 및 환경별 정책
- 새 앱은 개발·시험 환경에서 배포 파이프라인과 핵심 동작을 먼저 검증한다.
- 사용자에게서 해당 서비스의 운영 배포가 요청되었거나 장기 운영 지침으로 명확하게 지정된 경우, 비파괴적이며 사전 설정된 운영 대상에 자동 배포한다.
- 운영 DB 삭제·초기화, 권한의 대규모 변경, 데이터 이전, 새로운 유료 비용, 서명키 변경, 서비스 중단 위험이 큰 작업은 영향·복구 방법을 제시하고 별도 승인받는다.
- 배포 대상·호스팅·도메인·서명·비밀정보가 미설정이면 가능한 코드·CI·시험 환경을 완료하고, 막힌 항목만 정확히 보고한다. 미배포를 배포 완료라고 표현하지 않는다.
- `main` 병합 및 운영 배포는 자동 테스트·보안 검증 통과를 조건으로 한다. 실패 시 배포를 중단하고 수정하며, 이미 배포한 경우 복구/롤백 절차를 사용한다.
- 서비스별 배포 트리거는 변경 경로에 따라 분리한다. `notice/`의 변경만으로 `hr/` 운영 배포가 실행되지 않도록 한다.
- PC 설치 파일은 운영체제별로 빌드하고 서명·버전·호환성을 검사한다. 설치 파일 제공과 앱 자동 업데이트는 구분한다.
- 운영 배포와 실제 PC 설치·사용자 데이터 수신을 혼동하지 않는다.
