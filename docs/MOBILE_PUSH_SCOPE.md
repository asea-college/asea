# ASEA 모바일 앱 및 푸시 알림 개발 범위

## 목적
기존 Windows 앱 및 관리자 웹과 동일한 Supabase 프로젝트 `asea-workspace`를 사용하고, 교직원이 설치 가능한 Android 앱(우선) 및 향후 iOS 앱을 지원한다.

## 제품 요구사항
- 교직원 직접 가입(이메일 종류 제한 없음), 이름·부서 입력, 서버 관리자 승인, PC/모바일 공통 계정
- 전체/부서/개인 공지 목록, 상세 보기, 본문 블록 표시, 확인·동의·의견/설문 응답
- 공지 확인 여부는 서버 기준이며 중복 응답 방지; 여러 기기에 상태 동기화
- 기존 학교 일정표 정보를 원본 손상 없이 읽기 연동하고 원본 편집 화면으로 이동
- 푸시 알림 수신, 공지별 딥링크, 미확인 건수 배지, 수신 실패 시 앱 내 미확인 목록
- Android 알림 권한 요청(거부 시 서비스 사용 가능), 로그아웃 시 토큰 비활성화
- 잠금 화면에는 제목 등 최소 정보만 노출하고 민감한 본문/첨부 정보는 노출하지 않음
- 향후 그룹웨어·인사·예산·자산 모듈 확장을 전제로 모듈 분리

## 서버 및 보안
- 기존 `asea-workspace`의 `notice_*` 엔터티를 공통 기준으로 재사용.
- 장치별 푸시 토큰을 사용자 ID와 연결하여 저장. 서버에서 RLS 및 사용 권한 검증.
- 공지를 전송할 때 대상 사용자만 계산하고 발송한다. 기기 토큰과 FCM 서버 인증 키는 일반 클라이언트/공개 저장소에 노출하지 않음.
- 발송은 Supabase Edge Function 등 서버 기능에서 처리하고 idempotency, 재시도, 실패 기록을 구현.
- Android는 FCM, iOS는 APNs 연동을 포함한 경로를 구축한다. 기기 알림 수신은 OS 권한 및 네트워크 상태에 영향을 받으므로 전달 보장은 앱 내 알림함과 별도 검증.
- 운영 DB의 기존 일정·그룹웨어 데이터와 테이블을 변경하지 않음. 신규 DDL은 독립 마이그레이션으로 기록.

## 단계
1. Android 앱 소스/화면, 공통 로그인/공지 조회/응답 개발.
2. 서버 알림 토큰 저장/RLS, 푸시 전송 기능과 전송·수신 테스트.
3. APK 서명 체계, 버전 업데이트 및 GitHub CI 자동 빌드.
4. Android 실제 기기 및 PC 데이터 동기화 검증, 이후 iOS 확대.

## 배포 기준
PR 생성만으로 완료 처리하지 않는다. 기능별 테스트, 서버/클라이언트 연동, 설치 가능한 APK와 푸시 실기기 검증을 구분하며 운영 배포 전 안전성 확인을 수행한다.

**상태:** 범위 정의 완료. 이 문서 등록은 Android APK·푸시 배포 완료를 의미하지 않는다.
